# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project state

FastAPI backend for the legal-document RAG app. The API contract the frontend relies on is `../frontend/docs/backend-api.md` and `../frontend/lib/api.ts`; the backend's side of it (status codes, error `detail` strings, auth checks) is documented in `docs/IMPLEMENTATION.md` → API. Keep field names and error strings in sync with the frontend.

Implemented: Cognito JWT auth, `GET/POST /documents`, `DELETE /documents/{id}`, `POST /chat`, `GET /documents/{id}/file` (presigned S3 URL for the original), `GET/PATCH/DELETE /conversations[/{id}]` (chat history), `GET /health`. Pending frontend handovers live in `../frontend/docs/` (none at the moment) until the frontend folds them into `backend-api.md`. Not yet: reranker, Textract OCR backend, tenants/RLS, LangGraph, a second-model verifier.

`docs/IMPLEMENTATION.md` records what's built, the decisions behind it, and what has and hasn't been verified. `docs/CHUNKING_STRATEGY.md` is the agreed plan for replacing extraction/chunking (Docling, OCR routing, hybrid search); read it before changing `app/ingestion.py`. `docs/ANSWER_PIPELINE_PLAN.md` is the plan for the answer side (prompt fix, evaluation set, a fixed LangGraph pipeline, cross-references, claim verification); read it before changing `app/rag.py`'s answer flow.

## Environment

- Python 3.13, conda env `rag-backend` (`/opt/homebrew/anaconda3/envs/rag-backend`), also the PyCharm interpreter. Run `conda activate rag-backend` first.
- `requirements.txt` is a full freeze of that env (pip/setuptools/wheel excluded). After adding a package, regenerate it with `pip list --format=freeze | grep -viE '^(pip|setuptools|wheel)==' > requirements.txt`. Use `pip list --format=freeze`, not `pip freeze`, so conda packages don't turn into `@ file://` paths.
- Config comes from env vars / `.env` (template in `.env.example`) through `app/config.py`.
- Model downloads (Hugging Face hub: Docling's layout/table models and the chunk tokenizer; Docling's own artifacts) are cached in `.cache/` here (`CACHE_DIR`), not `~/.cache`. `app/__init__.py` sets `HF_HOME` / `DOCLING_CACHE_DIR` on import, so anything that imports `huggingface_hub` or `docling` must do so through the `app` package. Delete `.cache/` to force a re-download (about 500 MB).
- S3 is Floci locally (`AWS_ENDPOINT_URL=http://localhost:4566`, path-style addressing, SigV4). The buckets (`S3_BUCKET`, and Langfuse's) must already exist (created by `../infrastructure` (Terraform)), the app's with a CORS rule for the frontend origin (the browser loads files through presigned URLs); the app creates neither. For real AWS, unset the endpoint and keys.
- Langfuse (tracing) runs in the same compose: web, worker, ClickHouse, Redis, and a `langfuse` database in the app's Postgres. Its blob store is the Floci bucket `local-infra-local-langfuse`, which is created by `../infrastructure` (Terraform), not by the app. Its settings/secrets are in `docker/langfuse/langfuse.env`; the backend's `.env` needs the matching `LANGFUSE_PUBLIC_KEY` / `LANGFUSE_SECRET_KEY` (tracing is off without them).
- Local secrets are not committed: `.env`, `docker/postgres/postgres.env` (Postgres user/password, Langfuse's DB password) and `docker/langfuse/langfuse.env`; each has a `.example` template. The repo is the Casefile monorepo (`backend/`, `frontend/`, `infrastructure/`); its `.gitignore` and README are at the root. Don't add Claude co-author or attribution lines to commits.
- LM Studio must be serving on `LMSTUDIO_BASE_URL` with the `LLM_MODEL` and `EMBEDDING_MODEL` ids loaded (`curl localhost:1234/v1/models`). Without it, indexing retries and then fails, and chat returns 500.

## Commands

```bash
docker compose up -d --wait       # Postgres 17 + pgvector on :5432, Langfuse UI on :3001 (secrets in docker/langfuse/langfuse.env)
alembic upgrade head              # apply migrations
fastapi dev main.py               # API on http://127.0.0.1:8000 (main.py re-exports app.main:app)
python -m app.worker              # indexing worker (SQS consumer); without it uploads stay processing
pytest                            # unit tests (no DB or LM Studio needed)
pytest tests/test_rag.py::test_unverifiable_quotes_are_dropped   # single test
alembic revision --autogenerate -m "..."   # after changing app/models.py
python -m app.reindex [--all]     # queue documents from an older PARSER_VERSION (and failed ones) for re-indexing
python -m app.search "question" [--all] [--full] [--document NAME]   # retrieval only, no LLM: chunks + scores
```

## Architecture

- **Scoping**: `app/auth.py` verifies the Cognito access token (RS256 via JWKS, `iss`, `token_use == "access"`, `client_id`, no `aud`) and returns `CurrentUser`. Every query filters on `user.owner_id`, which is currently `sub`. When tenancy lands, change `owner_id` there. `chunks.owner_id` is denormalized so vector search filters without a join and RLS can be added later. Ids that aren't the caller's (or are malformed) return 404, never 403 or 422.
- **Ingestion** (`app/ingestion.py`, `app/worker.py`): the upload inserts the document as `processing`, commits, then streams the original to S3 through `app/storage.py` (bucket `S3_BUCKET`, key `uploads/<owner>/<doc id><ext>`; older documents keep `<owner>/...`). The object landing under `uploads/` fires an EventBridge "Object Created" event into SQS (`SQS_QUEUE_URL`; rule, queue and DLQ are in `../infrastructure`). `python -m app.worker` consumes it: one job at a time, each in a fresh child process (crash/OOM isolation, `INDEX_TIMEOUT_SECONDS` kill), extending the message's visibility every `INDEX_HEARTBEAT_SECONDS`, retrying transient errors with back-off until the queue's `maxReceiveCount` (the last attempt marks the document `failed`; the message goes to the DLQ). Delivery is at least once, so `index_document` only indexes `processing` documents and re-checks under a row lock before writing. Unsupported content (`ExtractionError`) fails at once without retries. The worker also fails documents stuck in `processing` for `INDEX_STALE_AFTER_SECONDS`. `app.reindex` sets documents to `processing` and sends `{"document_id"}` messages to the same queue. PDFs are converted `PARSE_PAGE_BATCH` pages at a time (bounded memory); over `MAX_PAGES` they fail. Indexing has three stages:
  - `app/parsing.py` turns the file into ordered elements (heading / text / table, with pages and bboxes). PDF, DOCX, DOC (needs LibreOffice) and images go through Docling, serialized by a lock. OCR runs only on regions without a text layer (`OCR_ENGINE`, default Apple Vision via ocrmac). txt/rtf are split into paragraphs directly.
  - `app/chunking.py` groups the elements into clauses, as described in `docs/CHUNKING_STRATEGY.md`. Clause numbers are detected in the paragraph text because Docling rarely labels contract clauses as headings. Sizes are measured in tokens of `CHUNK_TOKENIZER`; if that tokenizer can't load, it falls back to chars/4.
  - Embedding and storage: what gets embedded is `embed_text` (breadcrumb + content), while `content` stays literal. The chunks are written and the status set to `ready` in one commit, so retrieval only ever sees fully indexed documents.
  - Unsupported content sets `failed`, with the reason in `documents.error` (not exposed by the API). Bump `PARSER_VERSION` when parsing or chunking changes, and run `python -m app.reindex` to rebuild outdated or failed documents.
- **Chat** (`app/rag.py`): hybrid retrieval over the caller's chunks, optionally limited to `document_ids`. It takes vector candidates (HNSW, iterative scan) and BM25 keyword candidates, and fuses them with RRF. BM25 is computed in SQL (`bm25_search`) from `search_tsv`: section path weighted A and boosted, body weighted B, IDF over the chunks in scope. It's in SQL because `ts_rank` has no IDF and BM25 extensions aren't available on RDS/Aurora. Anything below `RETRIEVAL_MIN_SIMILARITY` cosine is dropped, so a keyword-only hit can't produce an answer. Retrieval is hierarchical (`retrieve_context`): the top-k chunk hits above the floor, plus matches on per-section embeddings (`sections` table: one row per top-level clause/exhibit/preamble, built by `chunking.build_sections`), score top-level sections; a section is sent whole (document order, within `RETRIEVAL_TOKEN_BUDGET`) only if it has 2+ hits, its heading matches the question's words, the question names its number, or its embedding clearly leads; other sections send only their hit chunks (`_expand_reason`). So a question about a section ("X's obligations") gets all its clauses. `search()` returns the scored chunk candidates; `python -m app.search` prints hits, section picks and the final prompt order. The LLM returns JSON (LM Studio structured output) with `[n]` markers pointing at numbered sources plus a quote per source. `build_answer` keeps only citations whose quote appears verbatim (whitespace-normalized) in that chunk, removes markers for the rest, and renumbers markers so `[n]` maps to `citations[n-1]`. If no citation survives, it returns `insufficient_evidence: true`. Every chunk sent to the LLM is also returned as `sources` (with location, bboxes and which `[n]` cites it), even on refusals.
- **History** (`app/conversations.py`, `routers/conversations.py`): `/chat` saves each answered question as a `Turn` in a `Conversation` (new one when `conversation_id` is omitted). Turns store citations/sources as a JSON snapshot, since re-indexing replaces chunks. Titles: generated by the LLM in a background task after the first turn (`generated_title`), overridden by the user's `custom_title`; `title_pending` tells the UI to poll. The LLM never sees earlier turns.
- **Tracing** (`app/tracing.py`): Langfuse traces `chat`, `title` and `index_document`, with `user_id` = owner and `session_id` = conversation id. LLM calls go through `langfuse.openai.OpenAI`, which records usage. Embeddings use plain httpx, because the wrapper patches every OpenAI client and LM Studio reports 0 embedding tokens; they are recorded by hand with the tokenizer count. Chat traces carry scores (`insufficient_evidence`, `context_tokens`, `cited_share`, ...). Details are in `docs/IMPLEMENTATION.md` → Tracing.
- **Models** (`app/ai.py`): uses the OpenAI SDK against LM Studio. Qwen3-Embedding vectors are truncated to `EMBEDDING_DIMENSIONS` (Matryoshka) and re-normalized. Queries get `EMBEDDING_QUERY_INSTRUCTION` and documents don't. With thinking models (Qwen3.x), LM Studio can return the whole structured output in `reasoning_content` with an empty `content`, so `complete_json` reads either one. The `vector(1024)` column size is hardcoded in migration `0001`, so changing the dimension or the embedding model needs a new migration plus re-indexing every document.
